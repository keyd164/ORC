# KTV 消费账单智能识别与数据工作台
## 完整开发实施方案 V1.0

## 一、项目定位

### 1.1 项目目标

开发一套基于微信小程序、Python、PaddleOCR、SQLite 和 Vue 3 的个人练习系统，实现：

1. 每日通过微信小程序上传 KTV 消费账单照片。
2. 自动识别账单中的编号、房间、时间、消费金额、支付方式等信息。
3. 将图片、OCR 原始文本和结构化账单数据保存到本地。
4. 对识别错误、缺失字段和异常账单进行人工校正。
5. 通过 PC 数据工作台查看每日营业数据、房间消费情况和识别质量。
6. 支持 CSV/Excel 导出，以及数据库与图片的完整备份和恢复。

### 1.2 已知业务特点

目前提供的两张样本具有以下特征：

- 来源于同一套 KTV 收银系统。
- 账单为固定纵向排版的热敏打印纸。
- 主要字段具有相对固定的位置和文字标签。
- 图片由手机拍摄，存在倾斜、阴影、背景干扰和局部遮挡。
- 不同账单的房间、金额、包厢类型和消费项目会变化。
- 同一账单可能被重复拍摄、重复上传，必须防止重复计入营业额。

因此，系统采用“通用 OCR + 固定版式字段提取 + 业务规则校验”的组合，而不是为每张图片单独编写程序，也不需要训练专用深度学习模型。

### 1.3 项目边界

第一阶段不开发：

- 云端服务器和多用户协作系统。
- 付费 OCR API。
- 自行训练图像识别模型。
- 复杂的会员管理、客户画像和个人信息分析。
- 自动识别所有可能的收银系统格式。
- 商业级权限体系和高可用部署。

第一阶段的目标是完成一个能持续使用、可追溯、可备份的本地应用。

## 二、技术架构

### 2.1 技术选型

| 模块 | 技术 | 作用 |
|---|---|---|
| 手机采集端 | 微信原生小程序 | 拍照、选图、选择日期、上传 |
| 后端服务 | Python + FastAPI | 上传、查询、识别任务、数据处理 |
| 图片处理 | OpenCV + Pillow | 图片旋转、裁剪、透视校正、增强 |
| OCR 引擎 | PaddleOCR | 本地文字识别 |
| 字段提取 | Python 正则表达式与规则引擎 | 识别账单字段 |
| 数据库 | SQLite | 账单、图片、识别结果和修改历史 |
| 图片存储 | 本地文件系统 | 原图、处理图和缩略图 |
| PC 工作台 | Vue 3 + Vite | 数据管理界面 |
| 数据可视化 | ECharts | 趋势图、统计卡片和分布图 |
| Excel 导出 | openpyxl | 生成 Excel 文件 |
| 自动化测试 | pytest | 后端和业务规则测试 |
| 版本管理 | Git | 代码管理 |

以上技术均可通过免费或开源方式使用。PaddleOCR 首次运行可能需要下载模型文件，之后可以使用本地缓存。

### 2.2 系统流程

```text
微信小程序
    |
    | 选择业务日期、拍照或相册选图
    v
FastAPI 本地后端
    |
    +---- 图片格式与大小检查
    |
    +---- SHA-256 重复图片检测
    |
    +---- 保存原始图片
    |
    v
OCR 任务队列
    |
    v
OpenCV 图片预处理
    |
    v
PaddleOCR 全页识别
    |
    v
固定字段提取
    |
    +---- 日期与时间解析
    +---- 账单编号提取
    +---- 房间信息提取
    +---- 金额与支付方式提取
    +---- 账单状态提取
    |
    v
业务规则校验
    |
    +---- 识别成功
    +---- 待人工复核
    +---- 识别失败
    |
    v
SQLite 数据库
    |
    +---- PC 数据工作台
    +---- 小程序历史记录
    +---- CSV/Excel 导出
    +---- 完整备份与恢复
```

### 2.3 两个前端共用一套后端

微信小程序负责手机采集，PC 工作台负责管理和统计。两者访问同一个 FastAPI 服务和 SQLite 数据库。

不建立两套数据，也不在小程序中单独保存一份账单数据库。

第一阶段使用本地运行模式：

- FastAPI 运行在个人电脑上。
- SQLite 数据库保存在个人电脑。
- 原始图片保存在个人电脑。
- PC 工作台通过本地地址访问。
- 手机通过同一局域网访问电脑后端。

开发者工具的本地调试与正式发布的域名、HTTPS 要求不同。第一阶段不购买公网服务器或域名；正式发布微信小程序时再单独评估平台要求。

|---|---|---|---|
| bill_no | 账单编号 | 字符串 | 必须 |
| merchant_name | 商家名称 | 字符串 | 可选 |
| bill_date | 账单日期 | 日期 | 必须 |
| room_name | 房间名称 | 字符串 | 必须 |
| room_type | 包厢类型 | 字符串 | 可选 |
| open_time | 开房时间 | 日期时间 | 必须 |
| checkout_time | 结账时间 | 日期时间 | 可选 |
| close_time | 关房时间 | 日期时间 | 必须 |
| print_time | 打单时间 | 日期时间 | 可选 |
| duration_minutes | 消费时长 | 整数 | 必须 |
| charge_type | 计费类型 | 字符串 | 可选 |
| package_name | 消费档位 | 字符串 | 可选 |
| item_amount | 消费项目金额 | 数值 | 可选 |
| total_amount | 消费合计 | 数值 | 必须 |
| receivable_amount | 应收金额 | 数值 | 必须 |
| received_amount | 实收金额 | 数值 | 必须 |
| payment_method | 支付方式 | 字符串 | 可选 |
| payment_amount | 付款金额 | 数值 | 可选 |
| change_amount | 找零金额 | 数值 | 可选 |
| cashier | 收银员 | 字符串 | 可选 |
| print_count | 打单次数 | 整数 | 可选 |
| bill_status | 结算状态 | 字符串 | 必须 |
| review_status | 复核状态 | 字符串 | 必须 |

其中，`business_date` 表示用户选择的归档日期，`bill_date` 表示从账单内容中识别的日期，两者必须分开保存。

“必须”表示业务系统希望获取的字段，不代表每张原始账单都一定打印了该字段。无法识别时应保存为空并提示复核，不允许凭空补值。

### 3.2 第二阶段可扩展字段

- 订房人。
- 收费方式。
- 卡余额。
- 卡积分。
- 会员卡号的脱敏标识。
- 多条消费项目。
- 优惠券或其他优惠金额。
- 退款、撤销或重新结账状态。

会员卡号和个人联系方式不是营业统计的必要字段，默认不提取、不导出。若保留完整 OCR 原文，应注意其中可能包含这些信息。

## 四、图片识别算法设计

### 4.1 第一阶段：图片预处理

每张上传图片保留原图，不对原图进行覆盖修改。

处理步骤：

1. 读取图片并校正 EXIF 方向。
2. 检查图片尺寸和文件格式。
3. 检测账单纸张边界。
4. 在能够可靠识别四角时进行透视校正。
5. 根据需要进行灰度转换、局部对比度增强和轻度降噪。
6. 生成用于 OCR 的处理图。
7. 保留原图与处理图的对应关系。

不能对所有图片无条件执行强二值化或锐化。热敏打印纸上的浅色文字可能因此丢失。预处理结果应通过测试样本进行比较。

如果纸张被其他物体遮挡、边界无法可靠定位，则退回原图或轻度增强图识别，并将受影响字段标记为待复核。

### 4.2 第二阶段：PaddleOCR 全页识别

OCR 输出至少保留：

- 识别文字。
- 文字所在的边界框。
- 可用的置信度信息。
- 模型名称与版本。
- 识别耗时。
- 识别失败信息。

原始 OCR 结果以 JSON 格式保存。这样以后即使修改字段提取规则，也可以重新处理已有 OCR 结果，而不必每次重新运行模型。

### 4.3 第三阶段：固定字段提取

优先利用账单中的标签进行字段定位，而不是单纯按文本顺序取值。

例如：

```text
账单号：R26102500006
房间名称：V15
开房时间：2026-10-25 13:39:00
实收金额：20
支付方式：手机支付
```

字段提取流程：

1. 在 OCR 结果中查找字段标签。
2. 根据文字位置寻找同一行或邻近区域的候选值。
3. 使用正则表达式和类型规则验证候选值。
4. 对多个候选值进行排序。
5. 将无法确定的结果标记为待复核。

对于固定版式，可在透视校正后的标准图片上设置局部识别区域。例如账单编号区域、时间区域和金额区域。只有在纸张位置已可靠归一化后，才使用固定区域坐标，避免手机拍摄角度不同导致裁剪错误。

建议优先采用“全页 OCR + 标签定位”，只有在特定字段反复识别失败时，再增加对应区域的二次 OCR。

### 4.4 第四阶段：业务校验

| 校验规则 | 处理方式 |
|---|---|
| 账单编号缺失 | 待复核 |
| 账单编号已存在 | 标记疑似重复账单 |
| 房间名称缺失 | 待复核 |
| 金额不是有效数值 | 待复核 |
| 金额为负数 | 标记异常，允许人工确认退款等情况 |
| 日期或时间格式错误 | 待复核 |
| 关房时间早于开房时间 | 标记异常 |
| 实收金额与应收金额不一致 | 提示复核，不自动判错 |
| 消费时长与开关房时间差异明显 | 提示复核 |
| 关键字段置信度低 | 待复核 |

消费时长与时间差异的阈值应允许配置。结账时间与关房时间可以不同，不应直接当作错误。

### 4.5 第五阶段：人工复核

复核页面采用左右布局：

- 左侧：原始账单图片。
- 右侧：识别出的结构化字段。
- 下方：OCR 原始文本及识别历史。

用户可修改字段并保存。

必须遵循以下规则：

1. 原始 OCR 文本不被覆盖。
2. 自动提取值与人工修正值分开保存。
3. 人工修正需要记录修改前后内容。
4. 重新识别不能删除之前的 OCR 历史。
5. 关键字段未确认时，不能将账单标记为已复核。
6. 对于模糊或遮挡内容，允许明确保留为空。

## 五、数据库设计

采用 SQLite。第一阶段建立六张主要数据表。

### 5.1 upload_batches：上传批次

| 字段 | 说明 |
|---|---|
| id | 批次唯一编号 |
| business_date | 用户选择的业务日期 |
| uploaded_at | 批次创建时间 |
| total_files | 图片数量 |
| status | 批次处理状态 |

### 5.2 images：图片主表

| 字段 | 说明 |
|---|---|
| id | 图片唯一编号 |
| batch_id | 所属批次 |
| business_date | 归档日期 |
| original_name | 原始文件名 |
| stored_path | 原图相对路径 |
| processed_path | 处理图路径，可为空 |
| sha256 | 图片内容哈希 |
| size_bytes | 图片大小 |
| status | 上传及识别状态 |
| uploaded_at | 实际上传时间 |
| duplicate_of | 重复图片对应编号，可为空 |
| error_message | 失败原因 |

### 5.3 ocr_runs：OCR 历史记录

| 字段 | 说明 |
|---|---|
| id | 识别记录编号 |
| image_id | 图片编号 |
| engine | OCR 引擎 |
| engine_version | 模型版本 |
| raw_text | 原始 OCR 文本 |
| result_json | 原始 OCR 结构化输出 |
| status | success 或 failed |
| error_message | 错误信息 |
| started_at | 识别开始时间 |
| completed_at | 识别结束时间 |

每次重新识别都新增一条记录，不覆盖历史结果。

### 5.4 bills：结构化账单主表

保存标准业务字段：

- `id`
- `image_id`
- `bill_no`
- `bill_date`
- `room_name`
- `room_type`
- `open_time`
- `checkout_time`
- `close_time`
- `print_time`
- `duration_minutes`
- `charge_type`
- `package_name`
- `total_amount`
- `receivable_amount`
- `received_amount`
- `payment_method`
- `payment_amount`
- `change_amount`
- `cashier`
- `print_count`
- `bill_status`
- `review_status`
- `duplicate_status`
- `created_at`
- `updated_at`

金额使用 SQLite `NUMERIC` 或以整数分保存，避免浮点数运算导致金额误差。建议项目内部统一以整数分存储，展示时转换为元。

账单编号不能直接作为图片主键。一张账单可能有多张照片，一张照片也可能重复上传。

### 5.5 bill_field_values：字段识别与校正记录

| 字段 | 说明 |
|---|---|
| id | 主键 |
| bill_id | 账单编号 |
| field_key | 字段代码 |
| detected_value | 自动提取值 |
| corrected_value | 人工修正值 |
| confidence | 字段置信度 |
| review_status | pending、confirmed、corrected 或 invalid |
| source_ocr_run_id | 对应的 OCR 记录 |
| updated_at | 修改时间 |

最终值规则：

- 存在人工修正值时，使用人工修正值。
- 否则使用自动提取值。
- 如果人工确认字段应为空，则必须有明确的“已确认空值”状态，不能误回退到原始错误值。

账单主表保存当前最终业务值，字段记录表用于追踪自动识别和人工校正过程。

### 5.6 field_edit_logs：修改历史

| 字段 | 说明 |
|---|---|
| id | 主键 |
| bill_id | 账单编号 |
| field_key | 修改字段 |
| old_value | 修改前的值 |
| new_value | 修改后的值 |
| edited_at | 修改时间 |
| reason | 可选说明 |

字段更新和修改日志应在同一数据库事务中完成。

### 5.7 索引与重复控制

建议建立以下索引：

- `images.business_date`
- `images.sha256`
- `images.status`
- `bills.bill_no`
- `bills.bill_date`
- `bills.room_name`
- `bills.review_status`
- `ocr_runs.image_id`

同一业务日期内，相同 SHA-256 的图片应提示重复。

如果不同照片识别出相同账单编号，系统应标记为疑似重复账单，而不是直接删除其中一条。用户确认前，疑似重复记录不得重复计入营业额。

## 七、后端 API 设计

统一使用 `/api/v1` 前缀。

| 方法 | 接口 | 功能 |
|---|---|---|
| GET | `/health` | 检查后端与数据库 |
| POST | `/batches` | 创建上传批次 |
| POST | `/uploads` | 上传单张图片 |
| GET | `/images` | 查询图片列表 |
| GET | `/images/{id}` | 图片详情 |
| GET | `/images/{id}/file` | 获取原图 |
| POST | `/images/{id}/recognize` | 重新执行识别 |
| GET | `/images/{id}/ocr-runs` | 查询识别历史 |
| GET | `/bills` | 查询账单 |
| GET | `/bills/{id}` | 查询账单详情 |
| PATCH | `/bills/{id}/fields` | 修改账单字段 |
| POST | `/bills/{id}/review` | 确认人工复核 |
| GET | `/dashboard/summary` | 统计卡片 |
| GET | `/dashboard/trend` | 每日趋势 |
| GET | `/dashboard/rooms` | 房间统计 |
| GET | `/dashboard/exceptions` | 异常记录 |
| GET | `/exports/bills` | 导出账单 |
| POST | `/backups` | 创建备份 |
| POST | `/backups/verify` | 校验备份 |

### 7.1 上传接口

`POST /api/v1/uploads`

采用 `multipart/form-data`：

- `file`：图片文件。
- `business_date`：归档日期。
- `batch_id`：上传批次编号。

返回：

```json
{
  "image_id": "唯一图片编号",
  "business_date": "2026-10-25",
  "status": "queued",
  "message": "图片已保存，等待识别"
}
```

小程序选择多张图片后，逐张调用上传接口。第一阶段限制为单个 OCR 工作线程，避免同时加载模型造成内存压力。

### 7.2 修改接口

`PATCH /api/v1/bills/{id}/fields`

提交需要修改的字段和值。后端必须检查字段是否允许修改，并在事务中更新账单主表、字段校正记录和修改日志。

### 7.3 工作台接口

`GET /api/v1/dashboard/summary`

返回：

- 累计账单数。
- 今日上传图片数。
- 今日已结账单数。
- 今日实收总额。
- 平均单笔金额。
- 待复核数量。
- 识别失败数量。
- 疑似重复账单数。

`GET /api/v1/dashboard/trend`

支持指定日期范围，按天返回：

- 上传图片数。
- 识别完成数。
- 已复核账单数。
- 已结账单数。
- 已结账单实收金额。

统计接口必须有明确的日期和账单状态口径，不能把待复核账单或疑似重复账单直接计入正式营业额。

## 十、数据导出和备份

### 10.1 CSV/Excel 导出

CSV 使用 UTF-8 BOM，避免中文在部分 Excel 环境中乱码。

Excel 建议包含三个工作表：

1. `Bills`：账单主数据。
2. `BillItems`：消费项目明细。
3. `ReviewLog`：人工校正记录。

导出遵循当前筛选条件，并显示导出时间和记录数量。

默认不导出会员卡号等非必要个人信息。

### 10.2 完整备份

备份包结构：

```text
backup_YYYYMMDD_HHMMSS.zip
├── app.db
├── uploads/
├── processed/
├── thumbnails/
└── manifest.json
```

`manifest.json` 保存：

- 备份时间。
- 数据库文件名。
- 图片总数。
- 文件列表。
- 文件 SHA-256 校验值。

备份过程应使用 SQLite 备份接口生成一致的数据库快照，再与图片文件一起打包。

### 10.3 恢复流程

1. 将备份解压到临时目录。
2. 检查数据库是否能够打开。
3. 检查图片文件是否完整。
4. 校验文件数量与哈希。
5. 确认恢复内容无误后替换正式数据目录。

不能只备份 SQLite 数据库而遗漏图片，否则恢复后会出现账单记录存在但原图无法打开的问题。

## 十一、测试与验收标准

### 11.1 样本数据集

第一阶段建议准备 50–100 张同一收银系统的账单图片。

至少覆盖：

- 光线正常。
- 阴影明显。
- 轻度倾斜。
- 纸张透视变形。
- 局部遮挡。
- 文字模糊。
- 不同金额。
- 不同房间。
- 重复图片。
- 相同账单的不同拍摄照片。

人工为测试样本建立标准答案，作为字段提取准确率的评价依据。

### 11.2 OCR 验收

建议第一轮以以下指标作为迭代目标：

| 指标 | 初始目标 |
|---|---:|
| 账单编号准确率 | ≥95% |
| 房间名称准确率 | ≥95% |
| 实收金额准确率 | ≥90% |
| 关键时间字段准确率 | ≥90% |
| 关键字段完全匹配率 | ≥85% |
| 原图保存成功率 | 100% |

这些数字是项目内部的验收目标，不是对 PaddleOCR 在当前图片上的性能保证。应以独立测试集上的实测结果为准。

### 11.3 业务验收

| 测试项 | 通过标准 |
|---|---|
| 多图上传 | 图片逐张保存，状态正确 |
| 重复图片 | 能检测并提示 |
| 重复账单 | 不自动重复计入营业额 |
| OCR 失败 | 原图保留，错误可追溯 |
| 人工修正 | 修改值生效，原始值保留 |
| 日期统计 | 与筛选后的明细一致 |
| 金额统计 | 与符合统计条件的账单一致 |
| 导出 | 记录数和字段值正确 |
| 备份恢复 | 数据库和原图均可恢复 |
| 稳定性 | 连续处理 20 张图片不崩溃 |

测试时应明确区分“识别完成率”和“字段准确率”。OCR 返回了结果，不代表结果一定正确。

## 十四、风险与解决办法

### 风险一：OCR 识别错误

解决办法：固定字段提取、置信度检查、业务校验和人工复核共同使用，不直接把所有 OCR 结果当作正确数据。

### 风险二：图片角度和阴影导致识别失败

解决办法：保存原图、预处理、按需局部识别；无法可靠恢复的字段进入人工复核。

### 风险三：重复账单导致营业额偏高

解决办法：图片哈希去重、账单编号重复检测、人工确认重复关系，统计时排除未解决的疑似重复账单。

### 风险四：SQLite 与图片文件不一致

解决办法：统一的存储服务、失败回滚或清理机制、完整备份和恢复测试。

### 风险五：小程序无法连接本地后端

解决办法：先在电脑上完成全部功能，再测试手机局域网访问。正式公网访问放在第二阶段。

### 风险六：敏感信息被保存或导出

解决办法：默认不提取会员卡号和个人联系方式；本地保存原图和 OCR 文本时限制访问，导出时默认排除非必要个人信息。

## 十五、最终验收定义

项目满足以下全部条件，即可认为 V1.0 完成：

1. 微信小程序可以选择日期、拍照、从相册选择多张图片。
2. 所有图片均能保存到本地，并建立唯一记录。
3. PaddleOCR 可以在本地完成文字识别。
4. 固定字段提取器能够识别核心账单信息。
5. OCR 原始结果、自动提取值和人工修正值分开保存。
6. SQLite 能够支持账单查询、筛选和统计。
7. PC 工作台可以展示每日账单数、实收金额、识别状态、异常记录及趋势图。
8. 可以导出 CSV/Excel。
9. 可以备份并恢复数据库与图片。
10. 无需付费 OCR API 或云服务器即可完成完整本地测试。

**最终技术路线：先完成本地 Python OCR 原型，再开发数据库和人工复核，随后建设 PC 工作台，最后接入微信小程序。**

这样可以先验证最关键的固定账单识别能力，再逐步完成整个系统，避免一开始同时开发多个模块却无法判断问题来源。
